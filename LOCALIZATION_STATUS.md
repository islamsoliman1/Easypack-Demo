## API and data contract

All API calls, including authentication, retries and CSV downloads, send `Accept-Language`. The server selects supported weighted `ar`/`en` ranges, normalizes regional variants, and defaults to Arabic for unsupported/malformed/missing headers. Every API response carries `Content-Language` and varies by `Accept-Language`; security-filter errors use the same request language.

Human-facing record properties are projected through an explicit allowlist. JSON adds `originalText` (source fields for that object) and `translationMissing` (fields without a reviewed translation). Nested inspection checks and historical snapshots follow the same rule. Codes, identifiers, enum values, email, serials, quantities, dates and attachment filenames retain their machine contracts. Existing input DTOs, authorization, version validation and transaction boundaries remain unchanged.

The frontend restores source fields before publishing responses to its cache. Forms, inspection copies and workflow inputs therefore retain original source values even when the UI is English. Display translation uses exact, reviewed dictionary entries; unknown text remains unchanged. English edit forms explain this and offer read-only reviewed previews. Source and translated seed names are both searchable. Response caches use a final language key component, preserving existing invalidation prefixes. Original data for the same base query is retained during a language-only refetch to keep open forms mounted; data from different languages is never stored as mutable translated business state.

CSV exports localize headers, order titles, status and boolean labels. UTF-8 BOM, CSV escaping/formula protection, numerical precision and UTC timestamps are preserved. On-screen dates continue using Africa/Cairo with ar-EG/en-GB formatting.

## Limits and upgrade safety

This release covers interface text and reviewed demo content. It does not translate arbitrary new notes, personal names, uploaded file contents, or newly authored records automatically. It does not provide paired Arabic/English authoring fields. Such text remains in its original language; the interface and edit dialogs explain the fallback, and API metadata identifies affected fields. This differs from the broader proposed storage/authoring stages in `LOCALIZATION_PLAN.md`.

Localization itself requires no migration, database reset, original-field rewrite, translation mutation endpoint, or backfill. The immutable dictionary is safe for both existing and fresh seed databases: changed user text is unmatched and preserved. Later catalog renames cannot change stored historical source snapshots or their reviewed exact-source translations. Localization rollback requires no data conversion. The integrated notification feature adds V101; its fresh-install and upgrade checks belong to combined application verification, not to a localization data backfill. Demo notification read state is shared by visitors, while each browser's language choice remains independent. Main and demo database migration histories remain separate and are not interchangeable.

Only `demo` was changed by this localization work. The active main Java application has a V13 notification subsystem; a separate chat supplied the demo notification backend/V101 migration and frontend components. The combined demo now wires the bilingual bell and inbox, notification routes, foreground refresh, and URL-backed task/preparation targets. Demo notification read state remains shared by visitors and is labelled accordingly. Combined verification passed the V101 upgrade, notification targets/read-state checks and restart preservation. Small reviewed compatibility fixes align existing demo behavior with main: template versions compare by value, permission collections accept all supported permissions, assigning the same worker is a no-op, file metadata does not load binary contents, and machine detail deep links are recognized by the SPA route allowlist.

## Reproducible checks

Run `node scripts/Check-Translations.mjs`, `npm run build --prefix frontend`, and Maven `test` from `backendjava`. The recursive catalog check includes 906 UI keys, 56 reviewed seed entries, notification/system content parity, interpolation variables, explicit API errors and query imports. `LocalizationTest` covers weighted locale fallback, concurrent request isolation and cleanup, response originals/nested snapshots, missing-content fallback, direct message catalog parity and export statuses. `LocalizedResponseMvcTest` verifies real Jackson serialization of declared typed lists, individual records and nested record/list responses: the response advice returns a JSON tree rather than a map list that Jackson could mistake for the original DTO list. The existing security/workflow unit tests remain part of the backend suite. Combined Docker/API/browser results are recorded separately by the verification owner.
